# 四专题合同

新建 Domain 固定生成以下四专题，域内各 Module 共用；不是每个模块再生成四份。框架面向不同运行形态，平台和项目机制按实际证据说明，不改变产物职责。布局与旧格式兼容见[稳定布局](../layout.md)。

| 入口 | 主定义对象 | 详细合同 |
| --- | --- | --- |
| `api.md` | 功能入口、调用契约、对象身份、字段与表示映射 | [接口与数据](api.md) |
| `downstream.md` | 调用者与消费者、责任交接、复用条件、修改影响 | [协作与影响](collaboration.md) |
| `configuration.md` | 固定业务规则、配置来源、优先级、生效分支与回退 | [规则与配置](configuration.md) |
| `lifecycle.md` | 状态推进、资源所有权、取消恢复、观测与事件关联 | [状态、资源与观测](lifecycle.md) |

每个 H3 以真实契约、对象、规则、状态系统、协作方或资源命名。总览链接到唯一详情，不能停在第二个总览。一个详情可以服务多个 Module，但必须写清差异；其他位置精确链接，不复制完整定义。

专题正文面向读者解释事实，不陈列源码证据。需要追溯时把少量代表性源码位置写入当前文件 frontmatter 的 `anchors.locations`；正文保留业务名称、协议身份、限定符号、修改职责与验证方式，但不出现仓库源码路径、行号或“证据”段落。移除 frontmatter 后，每个详情仍应独立回答行为、边界、失败与修改问题。

确无独立事实时，可以用简短“已核验边界”说明调查范围及事实所在位置。不得生成空表、空详情或用 Module 列表填充专题。

## 共同写作节奏

每个专题先给面向定位的总览表，再按真实事实逐项展开。总览不是正文替代品：每一行应链接到本文件详情或明确的唯一主定义。详情至少把“是什么”推进到“何时发生、由谁负责、怎样改变结果、失败会留下什么、从哪里修改和验证”。

专题之间按责任去重：

- API 定义调用承诺、数据身份和表示映射；功能与接口对应，不把内部方法混写成网络请求；
- Downstream 定义调用与交接责任、复用条件和修改影响，不重复完整字段字典；
- Configuration 定义改变结果的规则、取值来源、优先级和生效时机，不把工程规范或当前默认值当作运行事实；
- Lifecycle 定义状态推进、资源释放、观测和恢复；配置值与数据载荷引用对应专题，不重复完整定义。

复杂内容使用“总览表＋解释性图＋逐项正文”：表格负责精确字段、条件或责任映射，图负责方向、顺序、状态或关系，正文负责原因、边界、例外和恢复。只有五行的“本专题包括……代表入口是……”通常意味着仍停留在目录级摘要，应返回源码继续展开。

模块手册先用自然语言解释完整任务、职责和扩展方式，再引用专题细节。唯一主定义不意味着模块只能保留链接：直接结论应包含足够的前提、实现差异和边界，便于独立阅读或摘取。

旧六专题及 API/Object 一级分片继续支持；新生产不再独立生成 Object、Rule、State Machine、Infrastructure。局部更新优先原主定义，迁移须先确认、建立新落点、修复入链并回读，再按授权和读时哈希处理旧内容。不因文件名称变化增加 Module 或新的声明协议。
